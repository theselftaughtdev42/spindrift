{#- One game, as a row of the grid: its name, its availabilities, what became of it, and the control that removes it. Extracted when status arrived, because status is the first fact whose consequences are contained by a single row — it retints one cell and dims or undims the rest, and reaches nothing above it or below. Rendered both inside the whole catalogue and alone as the answer to the two endpoints that change one game in place, so the two can never disagree about what a row looks like. Add, rename and delete still answer with the whole list: each changes the list's membership or its order, so there is no single row for them to swap. `data-status` is the handle everything to do with the outcome hangs off — the tint the status cell wears and the dimming the rest of the row takes. It is absent rather than empty when nothing has been recorded, so "no status" is something CSS can ask about by the attribute simply not matching. `data-undecided` is the same shape of handle for the other axis: it is here when no cell in this row is the intended one, which is the state every game starts in and the one the filter above the grid isolates. Valueless and absent rather than a `true`/`false` pair, for the same reason — the question CSS asks is whether the attribute is there. It is derived here rather than sent by the endpoints as a class, and that is what makes the filter need no wiring at all: deciding on a platform answers with this row re-rendered from the database, the fresh copy arrives without the attribute, and it drops out of a filtered page on arrival. The same is true in reverse when an intent is cleared. Both paths already re-read `intents`, so both get the right answer for free. -#}
